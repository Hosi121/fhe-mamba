# DGX Spark runbook

The measured machine is aarch64, NVIDIA GB10, CUDA 13.0, compute capability
12.1. Hardware was checked on 2026-09-21. Configure your own SSH host; `dgx`
in historical study commands is the author's local SSH alias.
CPU and GPU share 128 GB nominal memory
([NVIDIA hardware guide](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)).
Use host `MemAvailable` and GPU utilization for preflight; `nvidia-smi` does
not provide a separate usable VRAM total on this host.

Start with [the reproduction guide](reproducing.md) for the pinned public
checkpoint, included coefficient bundles and portable generation command.

## Build

On a fresh Spark host, install CUDA 13.0, CMake >= 3.25.2, GCC/G++ 13, Make,
Git and Python 3. The following commands create separate dependency and
project checkouts. If matching dependencies are already installed, set
`FIDESLIB_SOURCE_DIR` and `OPENFHE_PREFIX` and skip their initial build.

```bash
mkdir -p "$HOME/fhemamba" "$HOME/fhe-deps"
git clone https://github.com/Hosi121/fhe-mamba.git "$HOME/fhemamba/cipher"
git clone --no-checkout https://github.com/CAPS-UMU/FIDESlib.git "$HOME/fhe-deps/FIDESlib"
git -C "$HOME/fhe-deps/FIDESlib" checkout --detach cd171f20f510eeca04c71d7b0034ef073829f761
(
  cd "$HOME/fhe-deps/FIDESlib/deps"
  ./build.sh "$HOME/fhe-deps/openfhe-fides"
)
cd "$HOME/fhemamba/cipher"
scripts/build_dgx_spark.sh
```

The upstream dependency script checks out OpenFHE v1.4.2 and applies its
FIDESlib patch; it recreates `deps/openfhe-src`, so run that preparation in
the fresh dependency checkout above. The project build preserves the installed
dependency and uses `~/fhemamba/spark/` for its own patched FIDESlib snapshot
and kernel. No B300 container or Slurm allocation is needed. `BUILD_JOBS`
defaults to 8. `FHEMAMBA_REMOTE_ROOT` overrides the default `~/fhemamba` root.

The build verifies the source snapshot, runs the 13 C++ contract tests,
and writes `spark/kernel/stage1_mamba2_decode_fideslib.build.json`. The runner
checks hashes of the native sources/configuration, executable and OpenFHE
shared libraries, and sets the matching library path. FIDESlib is linked
statically by its current build. Rebuild after native source changes.

## Payload

Prepare payloads on the Python development host; no Python ML installation is
needed for the native Spark runner. Calibration text and evaluation prompt
must be separate. Use held-out data representative of the intended workload.

```bash
.venv/bin/python experiments/export_m1_payload.py \
  --checkpoint checkpoints/mamba2-130m-hf \
  --output runs/spark-payload --tokens 8 \
  --cal-text-file /path/to/calibration.txt --cal-tokens 512 \
  --bound-cal-text-file /path/to/bound-calibration.txt --bound-cal-tokens 512 \
  --autoregressive-prompt-tokens 2 --autoregressive-generate-tokens 4
rsync -az runs/spark-payload/ dgx:fhemamba/payloads/mamba2-130m/
```

Do not reuse an old payload merely because its directory contains `sqnewton`.
Normalized recurrent state requires `carried_bounds.source=calibration_text`
and one `state_head_abs_max` per head in every layer's `meta.json`. Old assets
on this host lack these fields. The kernel rejects them before evaluation;
regenerate them rather than fabricating bounds or suppressing the check.

Payload calibration is not a model-quality certificate. The legacy export
prunes heads using the largest step size; this does not establish negligible
decay over the full interval. New metadata labels that approximation explicitly.
Use the [pruning audit and quality gate](research/2026-09-21-ssm-cryptographic-design.md#recheck-the-existing-head-pruning-argument-first)
before attributing long-context checkpoint quality to an exported surrogate.

### Scheduled normalization integration

`export_m1_payload.py --normalization-bundle <bundle.json>` opts a **new**
payload into the certified block, gated and dedicated final RMSNorm recipes.
The bundle format is `fhemamba-normalization-schedules-v1`, as generated by
`plan_normalization_schedules.py`. The exporter requires every site, checks
each real-arithmetic certificate and checkpoint epsilon, and regenerates the
polynomial references. Fixed-vector references must be finite and their norm
inputs must stay in the declared domains. The bundle hash and observed domain
violations are retained in `chain.json`.

The frozen 49-site Mamba-2-130M bundle is
[`config/mamba2-130m-normalization-20260921.json`](../config/mamba2-130m-normalization-20260921.json).
For the fixed two-token integration payload:

```bash
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 .venv/bin/python \
  experiments/export_m1_payload.py \
  --checkpoint checkpoints/mamba2-130m-hf \
  --normalization-bundle config/mamba2-130m-normalization-20260921.json \
  --output runs/scheduled-norm-payload --tokens 2 --cal-tokens 128 --device cpu
```

The built-in calibration text has 34 tokens; 128 is the cap, not a claim of
broader coverage. Use independent representative text for a new workload.

The native path uses the existing contiguous model packing and projection
weight folds, evaluating the same mean-variance polynomial with the tested
balanced DAG. Its inverse checkpoints use public stage bounds and Meta-BTS;
the scheduled layers' transient checkpoints also use Meta-BTS to protect the
normalization inputs. Carried-state refresh retains its configured policy;
the original variance remains live across refreshes. The final norm has its
own recipe and schedules gamma on the numerator branch. No evaluation
decryption is needed. Older payloads retain their original normalization.

Start with `dgx_spark_scheduled_norm_smoke.json` (one layer, two tokens,
maximum polynomial-circuit error 0.05). This is an experimental integration:
it retains the other exported nonlinearities and head mask, so it is **not**
the joint-gate surrogate that passed the 4,096-token plaintext screens.
Internal-refresh, full-chain and longer-session results must be reported
separately from the isolated vector RMSNorm measurements.
The [integration study](research/2026-09-21-normalization-integration.md)
records the failed ordinary-refresh control, corrected one-layer gate and
passing 24-layer/two-fixed-token gate. The full-chain manifest is
`dgx_spark_scheduled_norm_chain.json`; the matching payload still fails its
1,024-token plaintext quality screen, so this is not a long-context promotion.

### Joint gates and public activation domains

Add `--stabilized-gate-bundle config/mamba2-130m-gates-20260921.npz` to the scheduled export
command to include the joint write/decay gates and public-envelope SiLU fits.
The exporter verifies every gate certificate and binds domains/rates to the
checkpoint, then regenerates all references. The new joint payload format
requires the updated native kernel; older binaries reject it.

The [stabilized integration study](research/2026-09-21-stabilized-native.md)
records the exact frozen bundle, export command and payload-bound quality.
`dgx_spark_stabilized_smoke.json` and `dgx_spark_stabilized_chain.json` are the
one-layer and full-chain two-fixed-token manifests. Source, binary and payload
identity checks are the same as for the other Spark campaigns. Bootstrap and
state-calibration bounds still need separate horizon validation.

The full-chain manifest now passes with the corrected six-level joint-write
tail: maximum error **0.003311**, **1,192.95 s** evaluation and **831** physical
bootstraps. The study retains encoder and exhausted-level failures. This is
a `security=not-set` fixed-input gate; extend its horizon and repeat keys
before making a generation or performance claim.

For a matched comparison of state-coordinate maps, create a separate payload
from independent calibration text. This retains the frozen polynomials and
evaluation references, and replaces only state bounds:

```bash
.venv/bin/python experiments/calibrate_state_coordinates.py \
  --checkpoint checkpoints/mamba2-130m-hf \
  --payload results/m2_chain_payload_headclip \
  --calibration-text /path/to/train-calibration.txt \
  --calibration-description 'independent training split, first 512 tokens' \
  --tokens 512 --output-chain runs/row-state-payload \
  --output runs/row-state-calibration.json
```

`dgx_spark_row_state_ab.json` compares `ROW_NORMALIZED_STATE=0/1` using that
same payload and binary. Row mode requires a flattened `state_row_abs_max`
array of `num_heads * head_dim` elements. The default remains group scaling;
operation count and depth are unchanged by row mode. Both arms run even if
the first fails, so the experiment can diagnose a precision improvement.
Each arm is still subject to the unchanged five-step 0.05 gate.

## Run and compare

### Complete prompt-to-text generation

On the Python host, use the frozen stabilized payload with a matching native
build on Spark. This command prepares the entire prompt, transfers a new copy,
runs the encrypted recurrence and decodes the actual selected token IDs:

```bash
OMP_NUM_THREADS=2 MKL_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 .venv/bin/python \
  experiments/run_dgx_generation.py \
  --base-chain runs/stabilized-payload \
  --output-dir runs/generation-001 \
  --prompt 'The capital' --generate-tokens 4 \
  --ssh-host "$FHEMAMBA_SSH_HOST" \
  --remote-root "$FHEMAMBA_REMOTE_ROOT" \
  --joint-periodic-coefficients --joint-subring-encoding
```

Create `runs/stabilized-payload` and set the two host variables using the
[reproduction guide](reproducing.md). A normal remote clone has its own `.git`
and does not need `--remote-git-dir`. Both local and remote output directories
must be new for every run.
`--prompt-file` accepts a UTF-8 prompt file instead of `--prompt`.

The command checks checkpoint weights and copies the payload without changing
its operators or state bounds. It rejects observed polynomial-domain escapes
before launch. Prompt length is inferred from the complete tokenization;
server evaluations equal prompt tokens plus requested output tokens minus one.
It uses `dgx_spark_stabilized_generation.json` with that exact horizon and the
existing 0.05 error gate, full synchronization and zero diagnostic decrypts.
Generation is greedy with a fixed requested length; EOS does not stop it early.

The output directory contains `request.json`, `native.log`, archived Python
sources and their hashes, raw `results/`, and `generation.json`. The latter
decodes measured IDs, records reference text separately and marks mismatches
as failures. Do not substitute expected IDs for failed measured output.

This first functional path is a **single-process client-loop simulation**.
The client decrypts final hidden outputs, computes full-vocabulary logits and
selects/re-encrypts each next embedding. State and convolution FIFO remain
encrypted. It does not establish a secret-key-free server, encrypted token
selection or full-chain 128-bit security. Runtime optimization follows this
end-to-end gate.

The [first measured run](research/2026-09-22-client-generation.md) passes all
five evaluations and four generated tokens, producing `The capital of the
Republic of` at maximum polynomial-circuit error 0.009192. Evaluation takes
3,038.12 s, with 37.05 GiB peak RSS.

The [periodic-coefficient follow-up](research/2026-09-22-periodic-gate-coefficients.md)
evaluates the same request in **2,573.37 s (42.9 minutes, −15.3%)**, with all
generated IDs unchanged and maximum polynomial-circuit error **0.011767 <= 0.05**.
It preserves the polynomial coefficients, ciphertext levels and bootstrap count.
To use it, add `--joint-periodic-coefficients` to the command above, choose a
new output directory and point `--remote-root` at a matching build. The measured
candidate is `/home/kataiwa/fhemamba/gate-periodic-20260922`. The launcher records
the requested mode and checks that the native result actually used it.
The original root contains the baseline binary; it does not support the new mode.

The [subring encoder](research/2026-09-22-subring-gate-encoding.md) further reduces
the same request to **2,310.80 s (38.5 minutes, another 10.2%)**, with maximum
polynomial-circuit error **0.016255 <= 0.05** and unchanged IDs, operation
counts and levels. Add both `--joint-periodic-coefficients` and
`--joint-subring-encoding`, choose a fresh output directory, and use
`--remote-root /home/kataiwa/fhemamba/gate-subring-serial-20260922` for the
measured build. This keeps the 50.6-minute and 42.9-minute baseline roots intact.
The subring mode requires periodic coefficients; the launcher checks the
reported native mode. The two dedicated campaign manifests are
`dgx_spark_subring_gate_smoke.json` and `dgx_spark_subring_gate_generation.json`.

The [shared plaintext path](research/2026-09-24-shared-plaintext-preparation.md)
ports the packed executor's copy reduction and GPU NTT to Mamba-2. Its matched
full comparison measures **2318.10→2142.11 s (38.64→35.70 minutes, −7.59%)**,
with unchanged IDs, operation counts, levels and error gate. Add
`--gpu-plaintext-ntt` to the prompt launcher with a fresh current build; it
includes fast upload and preserves the subring optimization. The archived
source and measured commands live in the linked study. Historical build roots
remain evidence for their original modes.

### Kernel comparisons

From the Spark checkout:

```bash
python3 experiments/run_dgx_campaign.py \
  --manifest experiments/manifests/dgx_spark_replication_ab.json \
  --runner scripts/run_dgx_spark.sh \
  --env BINARY="$HOME/fhemamba/spark/kernel/stage1_mamba2_decode_fideslib" \
  --env INPUT_CHAIN="$HOME/fhemamba/payloads/mamba2-130m" \
  --output-json "$HOME/fhemamba/results/spark-replication-ab.json" \
  --resume
```

`--env KEY=VALUE` overrides manifest defaults and records the resolved values;
per-experiment settings still select the two algorithms. Spark manifests resolve
`BINARY` automatically, verify dependency metadata even on resume, and bind
every payload JSON/binary file to a content hash. For a different workspace also pass
`--env FHEMAMBA_REMOTE_ROOT=...` and `--env RESULTS_DIR=...`.

The baseline uses ring 65536 / depth 44 / scale 59, `security=not-set`,
5 GiB plaintext cache, output-only fused true BSGS, paired state, late residual
Meta-BTS and full backend synchronization. These are candidates on Spark.
`CUDA_LAUNCH_BLOCKING=1` is conservative on this machine. The 65 GiB B300 cache
is not a Spark default. Record setup, first/warm steps, total evaluation,
peak RSS, logical/physical rotations and bootstrap counts. ABBA order reduces
simple warm-up/order bias; it is not a statistical latency certificate.

The 2026-09-21 corrected build passes all four 24-layer/one-token ABBA runs.
A same-level plaintext-addition scale fix was required when small-cache misses
were encoded at their consumption levels. Mean peak RSS falls from 41.85 to
36.17 GiB with binary replication; evaluation latency is essentially unchanged
in this small sample. See [raw evidence and limitations](evidence.md).

A one-token pass does not test carried-state stability. Follow it with the
[five-step gate](../experiments/manifests/dgx_spark_autoregressive.json), with
fused output and paired state explicitly marked as candidates. No numerical
candidate becomes a default until every step decrypts, every polynomial-circuit
error is <= 0.05 and generated IDs match with zero diagnostic decrypts.
The earlier group-scaled five-step baseline matches all four generated IDs but fails the
error gate at step 2 (`0.08236`); its manifest skips the binary candidate on
that failure. Keep this failed artifact when investigating the residual error.
The later row-state comparison uses binary replication in both arms, with
the same new calibration and build. Row scaling passes at maximum error
0.02314 and a fresh-key confirmation passes at 0.04405; group scaling fails
at 0.18949. Operation counts and approximately
36.6 GiB peak RSS are unchanged. Calibration coverage and additional prompts
are still required before making row scaling a default.

An additional public scale floor `max(row, group/8, 1e-6)` passes the same
five-step gate at 0.04185 without changing operation counts. It reduces observed
coverage violations, but the maximum state/scale ratio still reaches 5.68.
Reproduce this conditioning-only ablation with
`regularize_payload_state.py` and `dgx_spark_row_state_floor.json`; the script
consumes existing independent calibration rather than evaluation references.
Broader calibration must fail closed if the polynomial trajectory is non-finite.

`COEFFICIENT_AWARE_PS=1` enables the coefficient-aware Chebyshev split planner.
Use `dgx_spark_chebyshev_ab.json` for a matched 24-layer/one-token comparison;
retain the same binary and payload in both arms. The artifact records selected
plan counts and predicted saved products alongside actual operation totals.
The flag remains opt-in, and a one-token gate does not cover carried state.
The first matched comparison passes at errors 0.01536 / 0.02299. Actual products
drop by 168 ct-ct and 546 ct-pt, exactly matching the planner; rotations and
98 physical bootstraps stay unchanged. A single timing pair is insufficient
to establish a latency improvement. See the linked raw artifacts in
[the evidence registry](evidence.md).

Keep raw JSON, the campaign record, build metadata and payload identity.
Curate small results under `results/dgx/`; keep large payloads and logs
outside Git. Validate curated results with:

```bash
.venv/bin/fhemamba validate-artifacts --require-commit path/to/result.json
```
