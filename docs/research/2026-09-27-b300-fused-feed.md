# B300 RNS/NTT fusion with ordered CPU preparation — 2026-09-27

**Not promoted.** With two CPU producers in both arms, one fresh full pair
improves **147.72 → 145.51 s (1.50%)**. Exact qualification and model gates
pass, but this small single-pair effect does not justify replacing the
preceding ABBA-qualified **37.20 s/generated token** baseline. The candidate
patch and source snapshots are retained; the active encoder is restored to
the preceding qualified source. No additional timing repetitions are added.

The [preceding two-worker study](2026-09-27-b300-parallel-prefetch.md) completed
its ABBA while this candidate was prepared. User steering then requested
moving forward instead of waiting for further repeated measurements, with
an improvement around ten percent sufficient to proceed. This follow-up uses
four qualification probes, one fresh prefix A/B pair and one fresh full A/B
pair. It does not automatically repeat ABBA. These one-pair results have a
narrower measurement basis than the preceding 14.07% result.

## Mechanism and ownership

The existing experimental `--fuse-plaintext-rns-ntt` path replaces each compact
plaintext's per-modulus RNS expansion kernels with input conversion in the
first NTT half. It reuses the exported `NTT_RESCALE` first half, then the
ordinary `NTT_NONE` second half, so no rescale epilogue runs. The same signed
residue lift and integer output are preserved. Both halves run in one stream
across all active moduli, avoiding materialized expanded inputs and separate
16-limb NTT batches. The earlier fusion trial remains negative evidence;
its CPU-placement/frequency variation did not establish intrinsic slowdown.

This follow-up retains the two CPU producers and their verified CPU 65/66
placement in both arms. It additionally removes a redundant completion wait
only when the fused path uses the persistent RNS workspace. The final device
completion barrier still runs before publishing the plaintext to the GPU
registry. A temporary workspace still waits before leaving its block, and
separate expansion still waits before NTT consumption on other streams.
No global ciphertext-lifetime or refresh barrier is removed.

The only measured source difference is this completion condition and its
comment in `fideslib_plaintext_encoder.cpp`. Enabling fusion is recorded in
the candidate command. Both binaries use identical compiler/link settings,
the existing inverse-FFT plan and unchanged FIDESlib archives. The candidate
incremental rebuild explicitly touches the changed translation unit after
extracting the deterministic source archive, preventing stale objects.

## Correctness and scope

Four fresh GPU probes pass **960 exact RNS/metadata cases and 36 encrypted
primitive cases**, covering both Mamba-2/3 patterns and rings 32,768/65,536.
The fused path and noncompact fallbacks are both reached. No numerical gate,
CKKS parameter, secret distribution, public weight or model polynomial changes.

The full workload remains Mamba-3 SISO 187M, 12 layers, five encrypted
evaluations and four generated tokens. Both arms keep ring 32,768 for ordinary
work, ring 65,536 for refresh, depth 44, scale 59, first modulus 60, two-pass
S2C-first refresh and `security=not-set`. Full IDs are `[315,279,1614,315]`,
with 484 bootstraps and zero evaluation decryptions. Both error gates stay
0.001. No new security level or full Mamba-2 performance is claimed.

The unchanged queue/runner tests and sanitizer coverage are inherited from
the preceding study; this GPU-side change uses fresh integrated qualification.
The same B300 GPU 4, CPU mask 64–68, NUMA 2, four OpenMP threads and CUDA 13.0.1
image are used. Native main-thread placement and both producers are observed;
container-entrypoint startup samples are retained separately. No host clocks
or governors are changed.

The prefix improves 1.64%. The full candidate's observed 36.38 s/generated
token is a single experimental sample, not the adopted performance claim.
It saves 5.97 seconds in upload/NTT while preparation wait grows 3.29 seconds.
Maximum polynomial-reference error is 4.7804e-7 and exact-reference error is
4.7178e-5, both below the unchanged 0.001 gates. Full peak RSS is essentially
unchanged, 26.29136 → 26.29169 GiB.

In the prefix, upload/NTT time falls **0.95937 → 0.60487 s**, while the
consumer's CPU-preparation wait grows **0.77536 → 0.98704 s**. Making the
consumer faster exposes work that was previously overlapped. The timers are
not an additive partition, but this observation explains why fewer GPU
launches need not yield a similarly large inference gain.

The new candidate-only Nsight prefix records **219,621 kernels**, down from
308,734 in the preceding two-worker trace. The 82,303 separate expansion
kernels disappear, and forward NTT kernels fall 75,962 → 69,152. Device-wide
synchronization calls fall **54,601 → 50,830**, exactly 3,771 fewer for the
compact prefix uploads. Summed kernel time is 2.94088 → 2.78258 seconds;
GPU activity interval union is 2.40072 → 2.24179 seconds. These reductions
confirm that the intended work disappears, while the fresh uninstrumented
pair determines the limited end-to-end effect.

The trace control is the preceding study's two-worker candidate, whose GPU
path is this trial's baseline. Only the new fused prefix is profiled, after
the fresh uninstrumented pair. Counts and diagnostic behavior may be compared;
cross-study profiler wall times do not determine adoption. Activity interval
union is not SM utilization or theoretical-peak efficiency.

## What this narrows

The preceding two-worker result still exposes 17.953 seconds of preparation
wait. Eliminating only that wait while fixing all other costs has a conditional
ceiling of **12.06%**, not a promised speedup. More workers also require a
larger admission window: the queue deliberately caps active producers at its
capacity of two. Merely raising a worker-count flag cannot create four-way
preparation under that existing bound.

A separate, previously identified candidate is reusing the inverse FFT of
immutable public diagonals before level-dependent scaling and rounding.
The [rejected final-coefficient cache](2026-09-25-weight-coefficient-cache.md)
failed to share across changing levels. A transformed-input cache would need
an exact encoder entry point, bounded storage, immutable public-weight
identities and a cold comparison including all first-use work. Summed CPU
encoding service overlaps GPU work and cannot be used as a wall-time saving
prediction. No further preparation mechanism is implemented in this trial.
